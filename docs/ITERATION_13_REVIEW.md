# Iteration 13 — the commit, the citation, and the assumption

Theme: **find the next thing that looks correct but is wrong at the layer the reader actually
consumes.**

Live figures are in [CURRENT_STATE.md](CURRENT_STATE.md). Figures quoted below are dated
findings from 2026-10-15/16 and are deliberately not kept current.

---

## 1. Baseline

The iteration-12 fix held. The refresh bot ran **14 consecutive scheduled builds**, 2026-10-02
to 2026-10-15, runs #38–#51, zero failures. Production served the current payload throughout.

Starting point: `a7c0ef3`, as_of 2026-10-15, ESDI 13.26, 184 events, 361 Python tests + 1
failing, 217 frontend tests.

That one failing test was real, and was the thread that unravelled most of this iteration.

## 2. The commit was never the thing being tested

`docs/CURRENT_STATE.md` is regenerated by `pipeline.run` on every build, and
`test_current_state_doc_is_in_sync` fails if it drifts. Both worked exactly as designed. The
file was still **stale in the committed repository for forty-one days and twenty-nine
consecutive bot commits** — from 2026-09-05, the first bot refresh after the file existed. It
has never once been correct in a bot commit.

The build wrote the file. The test read the file the build had just written, and passed. Nothing
checked the step between them: `git add data/processed web/public/data`, which never mentioned
the doc. **The tested layer was the worktree; the shipped layer is the commit.**

On the day it was found, the committed doc said as_of 2026-10-02 / ESDI 10.20 / 176 events,
beside a committed snapshot saying 2026-10-15 / 13.26 / 184.

### The guard that would have caught it could not run

`ci.yml` was written in iteration 12 for exactly this class of gap: test the committed tree,
with no build. It had **never run on a single bot commit**. CI runs #1–#7 are all human pushes
from 2026-10-02; the bot pushed fourteen times afterwards and CI fired zero times.

GitHub does not trigger `push` workflows for pushes authenticated with the default
`GITHUB_TOKEN`. It is a loop guard, and a reasonable one. The consequence here was a correct
guard, structurally unreachable on the only commits nobody reviews.

### What shipped

- **`pipeline/artifacts.py`** — one declaration of what a build produces. The manifest glob, the
  staging step and the suite's required-file list now all read it; they were three independent
  lists and the doc was in none of them.
- **`scripts/staging_paths.py`** — `refresh.yml` stages what the contract declares.
- **`scripts/verify_staged.py`** — refuses a commit whose index is missing a declared artifact,
  or whose mirror and manifest come from a different build than the snapshot. It gates
  publication deliberately: an internally inconsistent artifact is worse than none. Unlike
  `E <= esdi` it cannot rot — it compares a declared set against git's own index and contains
  no arithmetic.
- **`workflow_run` trigger on `ci.yml`**, which is not subject to the `GITHUB_TOKEN`
  suppression, checking out the commit the refresh *made* rather than the parent the event
  points at.
- Tests that **do not assert on this repository**: they build a throwaway one, stage it through
  the real contract, and assert on what the commit would contain — including the mutation that
  reproduces the defect exactly.

## 3. Every date got the previous date's citations

The source page writes `DATE,<ref>` — **the comma comes before the citation**:

```
5 April 2026,<ref name="Moscow Times database"/> 20 May 2026,<ref .../> 24 June 2026,...
```

Splitting a date cell on top-level commas therefore handed every date the *previous* date's
sources. The first date in a multi-date cell got nothing, the middle ones got their
predecessor's, the last got two. `_incidents_for`'s own docstring claimed the split "keeps each
date with the citation that follows it" — the opposite of what the source means.

This was not a display defect. `_confidence` is a pure function of how many distinct hosts are
cited, and confidence multiplies an incident's exposure by between **0.45 and 1.0** — a 2.2×
lever. The misalignment systematically starved the earliest strike at each facility and
over-credited the latest, and the latest strike is usually the incident driving that facility's
live exposure.

It also made the payload sensitive to harmless upstream edits: appending one date and one comma
to the Omsk cell moved a Kyiv Post citation off the 2026-07-06 strike and onto the 2026-10-08
one, downgrading the first from `probable` to `possible` and upgrading the second to
`confirmed`, in a single daily refresh.

| | before | after |
|---|---|---|
| incidents with no provenance at all | **30 of 125** | **0** |
| rows citing one article twice | 4 | 0 |
| citations dated *before* the event they document | **57** | 11 |
| confidences corrected | — | **63 of 125** |

The residual 11 are genuine: the page reuses one named ref across dates and across sub-facilities
sharing a row.

Two smaller citation defects went with it: a ref nested in an `{{efn}}` footnote was invisible
to a non-recursive scan (which is how the CPC marine terminal strike carried no provenance while
the page cites it in a footnote), and a ref whose body is a bare bracketed link rather than a
cite template was discarded **silently, with no `parser_warnings` entry** — against this
project's own rule about malformed source material.

**Headline effect: 13.26 → 11.26.**

## 4. One refinery, counted twice

The curated inventory calls it `refinery-novoshakhtinsk`; the strike table calls it
`novoshakhtinsk-refinery`. `refinery_registry.resolve()` maps both to canonical `novoshakhtinsk`
— and the same build called that function to produce `canonical_linkage` while the scoring loop
keyed facilities on the raw `asset_id` string and scored them as two plants: 2.62 + 1.43 = 4.05
refining points for a plant the denominator carries once at 3.13%.

**The iteration-5 red team predicted this exactly**, and it was dispositioned as "a known latent
fragility" that did not fire because no linked refinery appeared in the strike table. One
appeared on 2026-10-10. It fired for five days with the suite green.

The naming conventions make recurrence near-certain — curated ids are `refinery-<place>`, parsed
ids are `<place>-refinery` — so `refinery-orsk` and `refinery-mari-el` are one upstream edit
away from the same split.

Facilities now collapse onto one key per physical plant; the key is a real inventoried
`asset_id` rather than an internal token; and the fold is **disclosed**, because an
`event_count` of 6 on a plant the strike table lists once is otherwise unexplainable. Capacity
is unchanged — this removes a double count and revalues nothing.

**Headline effect: 11.26 → 10.67.**

## 5. A false retrieval date, shipping in production

`crea`, `gem_ggit` and `gem_goit` published `retrieved: 2026-10-15, status: current` for
evidence last genuinely edited on **2026-08-27** and **2026-08-30**. Forty-nine and forty-six
days of age reported as zero, with the word "current" beside them.

`actions/checkout` writes every tracked file with mtime = now, and the preference for the git
commit date was keyed on the registry's `release_expectation` column being `internal`. Those
three are git-tracked but registered as `versioned`, so they fell through to the mtime branch.

It never showed in development, because on a working checkout a file's mtime sits near its
commit date. It was wrong only on a fresh clone — which is every build that publishes.

Now keyed on whether git tracks the path, which is not a heuristic: tracked content cannot
change without a commit, so the commit date *is* when that evidence last changed.

## 6. A pumping station presented as a refinery

`classify()` returned `refinery` for every row of the first table without reading the name,
because that table is headed "Oil refineries". The upstream table files `NPS Samara, Prosvet`
there — Transneft's Samara LPDS, a trunk-line pumping, storage and blending station with no
crude distillation.

It scores zero either way (no capacity cell), and the project's own resolver already returned
`None` for it and listed it under `incidents_unresolved_to_registry`. So the classifier and the
registry disagreed, with nothing reconciling them, and the dashboard presented a pumping station
as a disrupted refinery in a 0.35-weight sector.

A row whose own name says it moves or stores crude is now classed by that name. A name that says
"refinery" still wins — some rows name two facilities at once
(`tuapse-refinery-tuapse-oil-terminal`), and re-sectoring those on a keyword would have moved
twelve incidents and 12 MTPA out of refining on the strength of a regex rather than of evidence.
That conflation is left open: see §12.

## 7. Writing a document could have stopped the data

`refresh.yml` gates its commit on the full suite. `ci.yml` has argued since iteration 12 that
"the set of things able to freeze publication must be as small as the job that publishes", and
applied that only to the frontend. Every prose lint stayed inside the gate.

**Measured, not theorised:** creating an empty `docs/ITERATION_13_REVIEW.md` turns the suite
red, because `test_the_handoff_cannot_lag_the_newest_iteration_review` compares the newest
review against markers in three other files. Writing *this document* would have frozen the daily
data publication — the September outage's exact shape, waiting on a routine documentation
action.

Fourteen tests that assert about this repository rather than about the payload are now marked
`repo_hygiene`. `refresh.yml` runs `-m "not repo_hygiene"`; `ci.yml` runs everything, where a
prose failure is loud and cannot stop the data. Verified both ways with the review file present:
the publication gate stays green and publishes, the full suite goes red and names the markers to
fix.

The three staging-contract tests are deliberately **not** marked. A commit that would publish a
new snapshot beside a stale document is precisely a reason to withhold a payload.

Four meta-tests keep the partition honest — a marker is a promise, and nothing was enforcing it.

## 8. The assumption the headline actually rests on

Decomposed by the evidence kind driving each facility's decay, the index is **52 modelled, 1
estimated, 1 observed**. Almost the whole number decays on an assumed reconstitution horizon —
150 days for a refinery — that no source supports.

The transmission saturation constant is worth **under one index point** and ships a six-point
sweep, a concentration split, four alternative formulations and a red-team verdict. The
reconstitution horizon shipped **no sensitivity anywhere**. `METHODOLOGY.md` calls these
horizons "the single largest lever" and `cannot_tell_you` says the decline "is modelled decay,
not evidence of repair" — both true, neither quantified.

Halving and doubling the horizons moves the headline between **5.45 and 18.58** against a
declared 10.50. A 3.4× band, previously invisible.

Now published in `snapshot.recovery_horizon_sensitivity` and rendered in the Methodology panel.
The sweep re-runs `build_index.build` with the fallbacks scaled rather than reimplementing the
scoring, and a test asserts its declared point reproduces the published headline exactly — if it
ever does not, the sweep is measuring something other than the model it sits beside.

## 9. The refining basis — proposed, not deployed

The numerator and denominator are drawn from different sources, and for the same plants those
sources disagree: **217.65 MTPA as scored against 206.00 in the denominator (+5.7%)**, 19 of 23
differing, TANECO scored at 17.0 against a registry 7.45.

Two consequences, pulling opposite ways:

- `refinery_inventory.json` told the reader that a uniform nameplate revaluation leaves exposure
  **invariant** because numerator and denominator scale together. That holds only if both share
  a basis. **Corrected in place** — a false reassurance about robustness is worse than an
  acknowledged weakness, and this needed no methodology decision.
- **Moscow and Volgograd are in the denominator, are live, and contribute exactly zero**,
  because their strike-table rows have an empty capacity cell. An unknown quantity scored as
  zero, inside the index. Worth **3.40 refining points / ~1.40 headline** — the index would read
  11.90 rather than 10.50. Disclosed qualitatively before; the **magnitude was never stated
  anywhere**. Now `snapshot.impairment_not_sized`.

Not fixed, deliberately: sizing those two from the registry would put two plants on a
like-for-like basis while nineteen stay on the strike table's. Which basis the sector uses is a
methodology decision. Four options, their measured effects and a recommendation are in
[REFINERY_CAPACITY_BASIS.md](REFINERY_CAPACITY_BASIS.md). **The index is unchanged.**

## 10. Operational hardening

- **`ci_data_changed.py` had two exit codes for three outcomes.** "No change" and "this script
  crashed" were indistinguishable, so any failure produced a **green run that published
  nothing** — no red X, no email, no log anyone reads. Now 0/1/2, and the workflow fails on 2.
  It also could not see a file the build stopped producing.
- **`.gitattributes` claimed `merge=ours`.** `ours` is not a built-in merge driver and none is
  configured, so git fell back to the text three-way driver and would write conflict markers
  **into `snapshot.json`** — which `-diff` then hides, because these paths print only "Binary
  files differ". Now `-merge`.
- **The cache was not saved on a failed run**, so the eleven-day September streak destroyed every
  entry and made its own recovery a cold fetch (562s against a 92s steady state) — and a cold
  fetch is the one state with no stale-cache fallback. `save-always: true`.
- **`git push` had no retry**, so a human pushing inside the job's window lost the day's data.
- **A failing refresh was invisible.** GitHub emails the owner on the *first* failure of a
  scheduled workflow and then goes quiet: an eleven-day outage produced one notification, on day
  one. Two consecutive scheduled failures now open one issue, updated on each subsequent failure
  and closed on recovery. Every run writes what it published to the run summary.

## 12. Deferred, with reasons

Carried into iteration 14. These are decisions, not oversights.

**Found this iteration, not acted on:**

- **Conflated multi-facility identities.** `tuapse-refinery-tuapse-oil-terminal` is one
  `asset_id` covering a refinery *and* a terminal, with 12 incidents scoring as refining at 12.0
  MTPA; `sheskharis-...-grushova-balka-oil-depot` covers two; and
  `ust-luga-multimodal-complex-ust-luga-oil-jsc-terminal-nevska` covers **four** and is truncated
  at exactly 60 characters by `_slug`, so any future row sharing that prefix collides into it.
  Splitting them changes which sector 12 incidents score in — a data decision needing evidence
  per facility, not a regex.
- **TANECO's 2.3× capacity disagreement** between the two bases, unchecked against a current
  public source. Large enough to move the sector alone.
- **The 60-character `_slug` truncation** as a general collision risk.
- **Asset identity coverage**: 40 of 85 distinct `asset_id`s are parser-generated and appear in
  neither the curated set nor the inventory; 80 of 184 incidents (43.5%) have no capacity anchor
  anywhere. Referential integrity is perfect (zero dangling `linked_asset_id`); the weakness is
  coverage. `oil_terminal` is the dominant gap and has no canonical registry at all.
- **"13 assertions never execute"** — a partial finding from the hostile-test red team, which hit
  a session limit before reporting which. The lead is real and unverified; re-run it first.

**Deferred from iteration 12, still deferred:**

- Real-browser **E2E tier** (Playwright). **Feasibility is now established, not assumed**:

- Print/PDF verification; the screenshot regression set; DOM component tests (vitest runs in
  `node`, so **no component renders in any test**).
- `dashboard_first_seen_build` and the as-published history. The 2026-10-10 backfill — 7

- Saved workspaces, command palette, the multi-page Analyst Report, clipboard image copy.
- GIE storage, GEM coal, the WRI per-unit retirement crosswalk, the transmission methodology

## 13. What this iteration is actually about

Three defects, three layers, one shape.

The **commit** was not the worktree the tests read. The **citation** was not attached to the
event the index scored. The **assumption** was not visible beside the number it produced.

In each case the component was correct and the seam between components was not, and in each case
a passing test was reading the layer before the one that ships. 367 tests passed over all three
of them.

The repair is not more assertions. It is moving each guard down one layer — to the commit, to
the citation's own publication date, to the model that actually produced the headline.
